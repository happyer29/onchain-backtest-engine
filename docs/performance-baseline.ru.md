# Измерение производительности

Бенчмарк измеряет конкретный опубликованный входной артефакт и сравнивает
эквивалентные пути исполнения. Требования к ресурсам и допуску определены в
[подробной архитектуре](architecture-deep-dive.ru.md), разделы 27 и 32.

## Команда бенчмарка

```bash
backtest benchmark TARGET_ARTIFACT_ID \
  --attempt-nonce SHA256 \
  --workload REPLAY_PACK_SCAN \
  --launch-route LOCAL_ARTIFACT \
  --capacity-days 1 \
  --batch-rows 65536 \
  --readahead 1 \
  --process-count 1
```

Замените `TARGET_ARTIFACT_ID` идентификатором проверенного локального артефакта,
а `SHA256` — новым nonce попытки. Команда публикует версионированный артефакт
`BENCHMARK` через обычный протокол атомарной публикации.

| Нагрузка | Входной артефакт | Путь запуска |
|---|---|---|
| `PARQUET_SCAN` | Snapshot | `LOCAL_ARTIFACT` |
| `REPLAY_PACK_SCAN`, `REFERENCE_REDUCER`, `OPTIMIZED_REDUCER` | ReplayPack | `LOCAL_ARTIFACT` |
| `FULL_BACKTEST`, `EMBEDDED_INFERENCE`, `FROZEN_INFERENCE` | Successful Run | `LOCAL_ARTIFACT` |
| `CONTROL_PLANE_ROUND_TRIP` | Successful Run | `DIRECT` или `CONTROL` |

До замера resolver проверяет тип артефакта, сохранённые зависимости, runtime
и режим inference. Замеры control plane используют один процесс.

## Порядок сравнения

1. Зафиксируйте одинаковые семантические входные данные и режим исполнения
   для обоих backend.
2. Сохраните в артефакте бенчмарка runtime, оборудование, размер batch,
   readahead, число процессов и native threads, состояние кеша.
3. Измерьте память однодневной нагрузки в отдельном дочернем процессе.
   Допускайте нужное число процессов только с учётом этого измерения.
4. Отделите прогрев от измеряемых итераций. Сравнивайте медианное время
   и требуйте одинаковый канонический хеш результата во всех итерациях.
5. Запишите wall/CPU time, throughput, private/total RSS с указанием метода
   измерения, page faults, swap и доступные счётчики процессного I/O.

Размеры batch: 32k/64k/128k/256k; readahead: 1/2/4; независимые процессы:
1/2/4. Один запуск с состоянием всегда выполняется одним последовательным
дочерним процессом. Повторение базового потока для capacity 7/30 имеет
семантику `REPEATED_INDEPENDENT_BASE_STREAM` и не является непрерывной
историей рынка.

`WARM`, `UNCONTROLLED` и `EXTERNALLY_COLD` — разные состояния кеша.
`EXTERNALLY_COLD` требует проверенного внешнего контроллера вытеснения;
без него команда отклоняется. Неконтролируемый запуск не доказывает работу
с холодным кешем.

Для `CONTROL_PLANE_ROUND_TRIP` изолированные артефакты, отдельная SQLite,
controller и готовность сервера подготавливаются вне измеряемого участка.
`DIRECT` измеряет `DirectJobExecutor`; `CONTROL` — настоящий loopback HTTP
submit, durable queue, supervisor, дочерний процесс, ожидание завершения и
типизированный запрос результата. Оба пути заново открывают опубликованный
Run manifest и проверяют канонический результат.

## Допуск оптимизированного backend Pump.fun

Программный допуск требует побайтового совпадения нормализованных audit,
ledger, fills, round trips, final balances и хешей результатов между reference
Parquet, reference ReplayPack и optimized ReplayPack. Каждый режим исполнения
проверяется отдельно; доказательство для одного режима не допускает другой.

Для производственного допуска дополнительно нужен репрезентативный точный
снимок внешних данных со следующими результатами:

- медианное время всей стратегии с ledger минимум в 2 раза меньше reference;
- одинаковые канонические результаты во всех измеряемых итерациях;
- peak private RSS не более 3 GiB для профиля 16 GB или 6 GiB для профиля 32 GB;
- отсутствие sustained swap и один последовательный child/native thread на запуск;
- объём clock пропорционален блокам/событиям, а не числу транзакций.

Производительность тестовых данных не доказывает достоверность источника
или скорость на внешних данных. Замер относится только к конкретным входным
данным, режиму, состоянию кеша и настройкам. Результаты FirstSwap не доказывают
производительность Pump.fun. Холодный кеш, нагрузки на 7/30 дней, извлечение
данных, ML и накладные расходы Control API требуют отдельных измерений;
универсальная пропускная способность или deployment SLO не заявляются.

## Воспроизводимые проверки на тестовых данных

```bash
.venv/bin/pytest -q -m performance \
  tests/performance/test_replay_30_day_capacity.py -s
.venv/bin/pytest -q -m performance \
  tests/performance/test_sniping_capacity.py -s
```

Эти проверки запускаются явно и используют детерминированные тестовые данные.
Храните отчёты рядом с соответствующими локальными артефактами. Перед допуском
оптимизации сравните эквивалентные входные данные до и после изменения,
канонические хеши, время, память, page faults, swap и I/O. Ускорение без
эталонной эквивалентности отклоняется.
