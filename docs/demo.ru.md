# Статические результаты на GitHub Pages

Статическая сборка показывает React-интерфейс версии 0.2 с заранее рассчитанными
результатами. Поддерживаются два набора: сгенерированные тестовые примеры и
выбранные результаты на реальном двухчасовом окне индексера. GitHub Pages
раздаёт интерфейс и JSON для просмотра; Python-сервер при просмотре не нужен.
Статический интерфейс всегда англоязычный, даже если в локальном приложении
был сохранён русский язык.
Подготовка отделена от публикации: push сам по себе не публикует сайт.

Адрес публикации — [GitHub Pages](https://happyer29.github.io/onchain-backtest-engine/).
Постоянная отметка показывает, какой набор открыт. Новая версия появляется по
этому адресу после успешного завершения deployment.

## Исторические результаты версии 0.2

Исторический профиль использует наблюдения OnchainDivers за окно решений
**1 сентября 2026 года, 00:00–02:00 UTC** (03:00–05:00 по Москве), полуоткрытый
интервал блоков `[443282098, 443304776)`. Подготовка включает ещё 4 096 блоков
для завершения позиций, открытых у конца периода. Этот хвост не расширяет окно
для новых входов.

В навигации доступны Overview, Strategy results, Launch strategy, Job queue,
Prepare data, Models and features, On-chain research, Artifacts and lineage
и Resources. Published dataset (`#/dataset`) показывает опубликованный интервал
и готовые бэктесты. Можно менять поля форм, выбирать стратегии и этапы ML,
открывать вкладки и фильтры; кнопки запуска и подготовки отключены. Страницы
очереди и ресурсов объясняют отсутствие рабочих данных.

На сайте можно выбирать готовые варианты стратегии, сравнивать их модели
исполнения и сводные показатели, листать сделки, открывать доступные рыночные
графики и прослеживать происхождение артефактов. Реальные наблюдения не превращают
смоделированные исполнения в реальные сделки: строгий replay и виртуальное
исполнение сохраняют свои обозначения. Если график недоступен или превышает
существующий лимит запроса движка, интерфейс показывает исходную типизированную
ошибку; публикация не подменяет её выдуманным или обрезанным графиком. Остальные
ошибки графиков останавливают экспорт.

Публикуются представления завершённых запусков. Полный исходный датасет
индексера, Parquet-снимки и Python-движок в браузер не загружаются. Новые запуски,
подготовка новых данных и применение изменённых параметров требуют локального
приложения. Изменения полей предпросмотра остаются в браузере и не меняют
опубликованные результаты. Рабочего API и действующей очереди задач на сайте нет.

Историческая выгрузка использует `backtest.static-history/v1`, рецепт
`indexer-two-hour-results/v1`, `synthetic: false` и версию `0.2.0`. Манифест
содержит окно UTC, интервал блоков, ID проверенных снимков и выбранных запусков.
Лимиты: 16 запусков, 8 192 ответа, 2 MiB на ответ, 256 MiB ответов суммарно и
4 MiB на манифест. Сборка и браузер проверяют хеши и отклоняют неподдерживаемые
запросы без обращения к рабочему сервису.

## Тестовые примеры

| Пример | Что показывает |
|---|---|
| Ончейн-исследование | 60 кошельков в четырёх заданных группах, 423 пары без Mayhem, 426 в режиме «Все» |
| Граф | Весь результат → группа → окружение кошелька; поиск, масштаб, отсечение слабых связей, покупки каждой пары |
| Исходные наблюдения | Повторные покупки, продажа, Mayhem, неизвестный режим и предупреждение об отсутствующей подписи создания |
| Copy Buy, строгий replay | Вход и исчерпанные попытки продажи при наблюдаемых резервах |
| Copy Buy, виртуальное исполнение | Тот же небольшой сценарий с закрытой позицией и явно обозначенным синтетическим финансированием продажи |
| Детали результата | Аналитика входов/выходов, история рынка, реальные попытки, точные суммы и происхождение тестовых данных |

Оба исследования рассчитаны с окном 60 секунд и минимумом два общих токена.
Алгоритм сравнивает **первую успешную покупку каждого токена каждым кошельком
внутри снимка**. Поздние повторные покупки не добавляют совпадения. Группы —
визуальное разбиение найденных пар; они не доказывают общего владельца или
координацию. Данные специально устроены так, чтобы показать навигацию и
ограничения метода. Это не исследование реального рынка и не доказательство
доходности стратегии.

Переключатель выбирает уже рассчитанный результат; фильтры графа меняют только
видимые связи. Произвольные периоды и окна анализа, подготовка снимков,
подключение источника, запуск стратегий, очередь и обновление данных доступны
в локальном приложении. На статическом сайте рабочего API и запуска задач нет.

## Подготовить тестовые примеры и открыть локально

Нужны Python 3.13, uv и Node.js 22.12+ (в CI используется Node 24).
Из корня репозитория:

```bash
uv sync --all-groups --frozen
npm ci --prefix frontend
npm --prefix frontend run demo:prepare
npm --prefix frontend run demo:build
npm --prefix frontend run demo:serve
```

Открой [локальное демо](http://127.0.0.1:18744/onchain-backtest-engine/).
Исследования находятся по `#/research`. Ссылки на результаты и происхождение
данных тоже используют hash routing: перезагрузка работает в подпапке проекта
на GitHub Pages. Сервер слушает только loopback; порт меняется переменной
`BACKTEST_DEMO_PORT`. Открытие `index.html` через `file://` не поддерживается:
нужен HTTP/HTTPS-сервер и браузер с Web Crypto.

`demo:prepare` вызывает существующие use cases подготовки, исследований и
эталонного исполнения в новой временной папке. Сетевые соединения заблокированы.
Ответы для интерфейса получаются через настоящий API внутри процесса.
Рабочий `data_root` и `configs/local.toml` не читаются; ClickHouse, пароль и
`.env` не нужны. Для реальных готовых результатов используется отдельный
экспортёр ниже: рабочие артефакты в публичную папку не копируются.

Генерируются папки, исключённые из Git:

- `frontend/demo-data`: манифест и JSON-ответы с адресацией по содержимому.
- `frontend/demo-dist`: готовый сайт, локальный worker графа, лицензии,
  `.nojekyll`, данные и перечень файлов `distribution.json` с SHA-256.
- `frontend/demo-test-results`: результаты браузерных проверок.

Начальный пример содержит 933 варианта запросов и около 4,3 МБ ответов.
Для каждой пары выгружены все исходные покупки. Сборка отвергает лишние файлы,
локальные пути и секретные поля, неверные размеры/хеши и превышение лимитов.
Браузер проверяет хеш манифеста, закреплённый в сборке, затем размер и хеш каждого
ответа. Потеря или повреждение файла показывается как ошибка, без обращения
к рабочему API. Хеши подтверждают целостность файлов, а не качество реального
источника.

Манифест фиксирует рецепт и точные ID примеров. После повторной генерации
собирай весь сайт заново: файлы разных сборок нельзя смешивать. Старые ID могут
стать недоступны. Для размещения подходит только `demo-dist`. SQLite, Parquet,
исполняемые манифесты и конфигурация источника туда не входят. Данные демо нельзя
импортировать в рабочий движок как снимки или результаты запусков.

## Выгрузить завершённые исторические запуски

Подготовь снимок и запусти стратегии обычным приложением версии 0.2 в отдельном
локальном data root. Создай локальный `selection.json` только с полями `source`
и `runs`. В `source` входят `name: "OnchainDivers"`, `start_utc`, `end_utc`,
`duration_seconds: 7200`, десятичные строки `from_block_ordinal` и
`to_block_ordinal`, список `snapshot_ids`. Каждый запуск содержит только ID
артефакта `id` и публичное название `title`. Экспортёр сверяет выбранные ID с
зафиксированными артефактами и проверенными интервалами решений снимков.

```bash
.venv/bin/python frontend/scripts/export-history.py \
  --data-root /path/to/isolated-data-root --selection /path/to/selection.json
npm --prefix frontend run demo:build
npm --prefix frontend run demo:test
```

Во время экспорта сеть заблокирована, конфигурация источника и секреты не
читаются. Выгружаются только разрешённые DTO для просмотра, полные страницы
сделок, доступные ответы графиков (включая типизированные ошибки) и ограниченное
дерево происхождения. Исходные артефакты остаются локально. Ошибка экспорта
сохраняет предыдущий публичный набор. При изменении данных сайт собирается заново.

Для CI упакуй **содержимое** `frontend/demo-data` в `pages-history-data.tar.gz`
и приложи архив к GitHub Release. В корне архива разрешены только `manifest.json`,
`manifest.sha256` и `responses/<sha256>.json`. Отдельно сохрани SHA-256 архива:
он закрепляет байты даже при замене release asset. Локальный импорт использует
ту же проверку, что workflow публикации:

```bash
.venv/bin/python frontend/scripts/import-history.py \
  --archive /path/to/pages-history-data.tar.gz --sha256 <archive-sha256>
npm --prefix frontend run demo:build
```

Импорт отклоняет лишние пути, ссылки, дубликаты, превышение лимита распаковки и
неверные хеши до замены распознанной папки демо. Лимиты архива: 128 MiB в сжатом
виде, 260 MiB содержимого файлов и 280 MiB распакованных tar-данных с заголовками.
Увеличенный исторический лимит вмещает полные графики отдельных сделок; браузерный
предел 2 MiB на ответ сохраняется. Сборка затем проверяет полный
перечень ответов и схему представлений. CI скачивает подготовленный архив с
правами чтения репозитория: к индексеру он не подключается и его секретов не получает.

## Проверить

```bash
npm --prefix frontend test
npm --prefix frontend run demo:build
cd frontend
npx playwright install chromium
cd ..
npm --prefix frontend run demo:test
```

Для установленного Chrome можно указать `BACKTEST_BROWSER_CHANNEL=chrome`.
Тесты поднимают сайт по `/onchain-backtest-engine/` на loopback-порту 18745;
`BACKTEST_DEMO_TEST_PORT` позволяет его изменить. Проверяются весь граф,
группы и окружение кошелька, покупки пары, смена режима, оба результата стратегии,
история рынка, происхождение данных, перезагрузка прямых ссылок, клавиатура,
все страницы продукта, редактирование форм с отключённой отправкой, фиксированный
английский язык при сохранённой русской настройке, тема, мобильная ширина
и повреждённые/отсутствующие файлы.
Транспортные тесты проверяют отказ для команд записи и неизвестных запросов.

Обычная команда `npm --prefix frontend run build` по-прежнему собирает рабочий
интерфейс в Python-пакет. Данные демо и подмена ошибок тестовыми ответами в него
не входят. CI проверяет оба профиля; общие проверки репозитория сохраняются.

## Опубликовать отдельным действием

Публикация требует отдельного решения. Команды выше не делают push,
не меняют настройки репозитория и не развёртывают сайт.

Когда публикация разрешена и код находится в GitHub:

1. В **Settings → Pages → Build and deployment** выбери **GitHub Actions**.
2. Чтобы появилась кнопка **Run workflow**, файл `demo-pages.yml` должен быть
   в основной ветке. В **Actions → Static demo / GitHub Pages** выбери нужную
   ветку или ревизию.
3. Выбери **dataset: synthetic** для тестовых примеров либо **dataset: historical**
   и укажи **data_release_tag** и **data_sha256** для импорта release asset
   `pages-history-data.tar.gz`. По умолчанию выбран synthetic.
4. С выключенным **publish** выполняются только проверки, с включённым — ещё
   и публикация проверенной сборки. В обоих случаях выполняются транспортные
   и браузерные тесты. Задание развёртывания
   получает только разрешения Pages/OIDC; загружается лишь `frontend/demo-dist`.
5. Открой адрес из результата deployment. Локально подготовленная ссылка
   не означает, что сайт уже опубликован на GitHub Pages.

Workflow запускается только вручную, версии Actions закреплены по коммитам.
Доступность Pages зависит от аккаунта/репозитория и настроек защищённого
окружения. См. документацию GitHub о
[workflow для Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
и [выборе источника публикации](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

Нормативные ограничения и лимиты:
[deep dive §34.3](architecture-deep-dive.ru.md#343-статическая-демонстрационная-сборка).
