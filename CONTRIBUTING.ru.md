# Участие в разработке

Спасибо за интерес к On-Chain Backtest Engine. Проект принимает небольшие, проверяемые
изменения, которые сохраняют детерминизм, точность относительно источника и
поведение `fail-closed`.

## Перед началом

1. Прочитайте раздел «Как читать документ», §3.4, затрагиваемые разделы и §38
   [подробного описания архитектуры](docs/architecture-deep-dive.ru.md).
2. Проверьте существующие обращения, чтобы не дублировать работу.
3. Для существенного изменения сначала откройте запрос функции и опишите
   ограниченный вертикальный срез.

Обычная функция или рефакторинг не меняют нормативную архитектуру. Если
предложение требует архитектурного отклонения, сначала необходимо явно
согласовать изменение подробного описания архитектуры и его последствия.

## Локальное окружение

```bash
uv sync --all-groups --frozen
source .venv/bin/activate
backtest --help
```

Никогда не коммитьте `.env`, `configs/*.local.toml`, содержимое `var/`,
учётные данные, адрес частного индексера или извлечённые данные.

## Рабочий процесс

1. Создайте отдельную ветку от актуального `main`.
2. Опишите в PR затронутые архитектурные разделы, инварианты и способы
   проверки отказов.
3. Сделайте минимальное целостное изменение вместе с семантикой отказов и
   тестами.
4. Обновите пользовательскую документацию, если меняется наблюдаемое поведение.
5. Запустите полный набор обязательных проверок.

```bash
.venv/bin/ruff format --check src tests
.venv/bin/ruff check src tests
.venv/bin/mypy src/backtest
.venv/bin/lint-imports
.venv/bin/pytest --cov=backtest --cov-report=term-missing
```

Проверки реального источника и производительности должны оставаться явными,
доступными только для чтения и ограниченными. Не добавляйте `skip`/`xfail`,
скрытую обработку исключений или ослабление покрытия ради зелёного CI.

## Запрос на слияние

Хороший запрос на слияние содержит:

- короткое объяснение проблемы и результата;
- затронутые слой, сценарий использования и порт;
- последствия для идентичности, причинности, точности, детерминизма и ресурсов;
- случаи отказа и способ их проверки;
- выполненные команды и их результат;
- снимки экрана для видимых изменений интерфейса без секретов, путей, адресов
  кошельков и чувствительных идентификаторов артефактов.

Сохраняйте запрос на слияние небольшим. Несвязанную очистку и рефакторинг лучше
вынести в отдельное изменение.

## Сообщения об ошибках и безопасность

Для обычных ошибок используйте шаблон отчёта об ошибке. Уязвимость или возможную
утечку данных нельзя публиковать в открытом обращении — следуйте
[политике безопасности](SECURITY.ru.md).
